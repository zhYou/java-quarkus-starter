# 数据库路线与维护成本

默认普通 PostgreSQL，用 Citus 提供可运行的分片示例。先在单库通过索引、SQL、连接池和容量规划解决问题，再依据容量、写入或隔离需求决定是否承担分布式运维。以下维护成本是工程判断，采购价格取决于区域、负载、可用性要求和服务合同。

| 路线 | 原生能力与水平扩展 | 维护与成本考虑 | 本模板位置 |
|---|---|---|---|
| PostgreSQL 单库与原生分区 | 分区有助于大表管理；不自动把写负载分到多台独立服务器 | 组件少，托管备份和升级成熟；通常适合作为起点 | 默认、完整实现 |
| PostgreSQL + Citus | 扩展在数据库侧路由分布表；不是 PostgreSQL 核心自带的多机分片 | 保留 PostgreSQL 协议；增加协调/worker、分布键、扩容及备份约束 | 真实三节点示例，无生产 HA |
| MySQL InnoDB 与原生分区 | 常规 InnoDB 分区仍在一个 MySQL 实例内 | 单库易维护；多机分片需另选方案，复合键、SQL 与事务要重新验证 | 备选，未实现 |
| MySQL NDB Cluster | MySQL 的 NDB 分布式存储引擎，区别于 InnoDB | 需要针对 NDB 的节点运维和行为评估；不能视为无成本切换 | 专门场景备选 |
| MySQL + Vitess | 在 MySQL 之上提供路由和分片控制 | 增加代理/控制面、拓扑与运维知识；适合有明确规模需求的团队 | 备选，未实现 |
| TiDB 等兼容数据库 | 独立的分布式 SQL 数据库，兼容 MySQL 协议和常见语法 | 要评估 SQL 差异、最小资源、升级和供应商服务；兼容不等于所有行为相同 | 备选，未实现 |
| 云商分布式产品 | 按具体产品确认分布式引擎、代理和兼容层 | 托管减少部分运维，可能增加供应商依赖和迁移成本 | 采购时独立验证 |

MySQL 路线适合已有 MySQL 数据、经验和运维体系的团队。若只是需要可靠的普通业务数据库，选择托管 MySQL 同样合理；本模板采用 PostgreSQL 是已批准的基线。换驱动不足以完成迁移，还需改迁移 SQL、UUID/时间类型、权限和测试环境，并重新运行事务、并发、备份与真实产物测试。

云原生表示应用可容器化、受探针管理、外置配置并可观测；它不要求第一天部署分布式数据库。计算、存储、网络、备份、值班、升级和事故恢复共同构成总成本。本地 Citus 只在明确需要时启动，普通检查不会隐式启动多节点环境。

资料：[PostgreSQL 原生分区](https://www.postgresql.org/docs/18/ddl-partitioning.html)、[MySQL 分区](https://dev.mysql.com/doc/refman/8.0/en/partitioning.html)、[TiDB 兼容性](https://docs.pingcap.com/tidb/stable/tidb-faq/)、[Vitess 文档](https://vitess.io/docs/)。具体产品版本和限制以采用时官方文档为准。
